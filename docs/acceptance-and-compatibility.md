# V0 acceptance and downstream compatibility

These are chosen release requirements, not results. No check below has passed merely because it appears in this document. V0 is finished only when the required evidence exists for the distributed candidate, covering the complete [Consulting Core 1.0.0 profile](consulting-core-profile.md), [Agent Workflow](agent-workflow.md), [artifact contract](contracts.md), and [local trust contract](local-trust-and-file-safety.md).

## Evidence and release decision

Keep a small versioned fixture corpus and a release evidence index. Each check records its ID, candidate commit and package hash, fixture hashes, command or review procedure, tool versions, environment, date, result, and links to logs or artifacts. Results are `pass`, `fail`, `not_run`, or `not_applicable`; the last requires a stated reason tied to a contract, never lack of time or credentials. Redact machine paths and tenant identifiers before publishing.

All required automated and review checks below must pass. A skipped, flaky, manually repaired, or unrun supported path leaves v0 unfinished. Fix the defect and rerun its affected cases; do not rewrite the expected model to match an incorrect result. Record intentional expectation changes with the changed process requirement. The release evidence index distinguishes automated checks, model-assisted reviews, human reviews, actual host sessions, and tenant observations.

Tenant access is not a prerequisite for installation, ordinary CI, or a portable v0 release. The required downstream deliverable is the compatibility profiles, local fit checks, reproducible qualification packs, and accurate evidence status. A named product's **verified import** or **verified round trip** claim requires its actual corresponding test; unavailable access remains `not_run`. This follows the agreed interoperability baseline and does not waive any Consulting Core feature. A known defect in OpenBPMN's valid output blocks release. A documented consumer limitation restricts that consumer's claim without removing the concept from Consulting Core.

## Corpus

Use authored synthetic evidence with explicit licensing and no private interview data. The existing [automotive AR discovery source pack](../eval/fixtures/automotive-ar-discovery/source-pack.md) remains one case. Fixtures are test assets, not proof of deployments, ROI, or measured operational improvement.

| Family | Minimum release content | Expected evidence |
| --- | --- | --- |
| `notation` | At least one small positive fixture for every Supported row, every listed event placement, both legal boundary interruption modes, both subprocess presentations, and every materially different attribute/reference rule. Include negative counterparts for each enforced rule and each Deferred family. | Requirement-to-fixture manifest; Structured Process Evidence; expected semantic projection; expected findings; generated BPMN, SVG, DI observations. |
| `composition` | Eight combined cases: lane ownership; multi-participant messaging; timer/error recovery; event-based competition; inclusive/parallel joins; nested expanded/collapsed subprocesses with same-file Call Activity; loop/multi-instance; data and intentional documentation. At least one contains three participants, nested lanes, 40 flow nodes, and 60 connectors. | Expected graph, visible-element set, review scenarios, visual reference, and full bundle. |
| `discovery` | Six evidence cases: automotive AR disagreement; purchase approval/rework; startup customer onboarding with external handoff; support escalation/timer; employee offboarding with parallel controls; service incident with a subprocess and data dependencies. | Source pack, assertion inventory, hidden-from-model reviewer expectations, allowed clarifications and answers, required/forbidden model facts, correction requests. |
| `adversarial` | Every trust-contract case, plus malformed/oversized/deep input, stale Handoff version, duplicates, unknown references, illegal placement, missing DI, deferred semantics, unsupported namespace, renderer failure, and bundle commit failure. | Exact failure class, diagnostic code, allowed artifacts, pre/post filesystem hashes, absence of disclosure. |
| `scale` | Deterministic seeds for 25, 100, and 250 flow-node models; largest case has 500 connectors, five participants, ten lanes, depth-four subprocess nesting, and labels up to 120 characters. | Repeatable generation recipe, reference machine, latency samples, peak memory, geometry results. |

The coverage manifest expands event definitions into their permitted placements; counting “Message Event” once does not cover start, catch, throw, boundary, and end behavior. Include forbidden placements and relationships, such as throwing timers, non-interrupting error boundaries, cross-scope links/Sequence Flows, internal Message Flows, and illegal event-based gateway targets. Test named reference resolution, category-backed Groups, standalone Data Input/Output DI, nested lane membership, subprocess contents, and Call Activity targets explicitly. One compact fixture may satisfy several requirements, but a count cannot replace coverage.

At least two discovery cases must be held out of shipped skill examples and authored before the release run. The agent sees only the evidence and permitted human answers, never the expected graph or scoring file. Authored answer scripts can make regression reproducible; the host must interpret them and run the real CLI, not replay prebuilt artifacts. Holdouts are a guard against example dependence, not a claim of statistical generalization.

## Automated checks

| ID | Check and exact release threshold |
| --- | --- |
| `CORE-01` | **Coverage:** every supported concept, placement, attribute rule, and referenced profile constraint maps to at least one passing positive case; every invalid/deferred rule maps to a passing negative case. Zero unmapped requirements, unimplemented cases, or blanket snapshot approvals. |
| `CORE-02` | **Input and identities:** every accepted input and requested Handoff validates against its versioned schema. Unknown versions, illegal union combinations, duplicate IDs, and dangling references fail precisely. Renaming, rewording evidence, changing layout, and adding a sibling preserve 100% of identities for retained elements. Removed identities are not reassigned to different meaning. |
| `CORE-03` | **Interchange:** every Clean Export passes the full locally shipped OMG BPMN 2.0.2 XSD set plus semantic and profile validation. The selected `libxml2-wasm@0.7.2` supplies the standards XML/XSD check independently of `bpmn-moddle`; replay that runtime check in CI, without adding a second XSD engine. Pin schema bytes and checksums. Every negative fixture triggers its expected code/category; no invalid fixture returns Clean readiness. A `bpmn-moddle` round trip is not an XSD check. |
| `CORE-04` | **Meaning:** the independently reviewed expected semantic projection equals the normalized input model and the post-serialization/post-layout projection for every positive fixture. Compare types, names, containment, references, responsibility, conditions/defaults, event definitions/interruption, loop markers, data direction, and intentional documentation. Zero added, dropped, or changed facts. Do not derive expected projections with the production compiler. |
| `CORE-05` | **DI:** 100% of intended visible elements have the right DI type and plane, finite positive shape bounds, resolved references, and useful connector waypoints. Bounds/labels stay inside their declared containers; boundary events intersect only their host border. Contents of collapsed subprocesses remain semantic and available through their declared secondary diagram; call targets retain their referenced same-file process. No unexplained missing-DI warning. |
| `CORE-06` | **Rendering:** every positive fixture imports into the pinned `bpmn-js` Viewer, selects every declared diagram, and renders without error, dropped visible elements, unknown notation, or unclassified warning. Generated SVG parses, contains its full intended visible-element set, and has no scripts, external loads, or unresolved font dependency. Check text/marker completeness against expectations. Viewer checks exercise a consumer, but share a dependency with a Viewer-based production renderer and are not an independent BPMN implementation. |
| `CORE-07` | **Determinism:** ten fresh runs of each notation/composition fixture produce byte-identical BPMN and SVG under the same pinned environment. Quality Report semantic content is identical after normalizing only documented operational fields such as output paths; findings order and identifiers remain stable. Across supported OS/Node environments require identical semantic projection, element identities, and DI geometry; raster antialiasing differences do not constitute semantic drift. |
| `CLI-01` | **All four commands:** test documented path/stdin inputs, JSON/human modes, `--help`, versions, malformed usage, read-only behavior of `validate`/`capabilities`, explicit render output, all exit classes, and empty/Unicode/space-containing paths. JSON stdout is exactly one parseable result, with diagnostics on stderr. No command needs a prompt, Host Agent, secret, network, or undeclared executable at runtime. `generate`/`render` use the documented local browser prerequisite; test missing, incompatible, and explicitly selected browser paths. `validate`/`capabilities` work without a browser. |
| `CLI-02` | **Export matrix:** Clean, Snapshot, and Invalid Expert cases match the quality/export contract, including unresolved questions, advisory findings, approved omissions, blocking validity, unavailable preview, and a failing renderer. No human lifecycle label is inferred or inserted into BPMN. No Quality Report or internal evidence metadata appears in Clean XML; intentional standard BPMN documentation remains intact. Check every declared outcome and flag combination. |
| `SAFE-01` | **Trust and persistence:** every acceptance case in the local trust contract passes. Inject failure at each generation and staged replacement boundary; for handled failures, old bundle hashes are identical and first-run destinations absent. Test collisions and symlink/path escape refusal; cleanup; secret redaction; payload-free logs; inert prompt/script/XML payloads; explicit-only Handoff; and nonpersistent invalid override. Test process interruption separately against the documented recovery guarantee rather than equating exception rollback with power-loss atomicity. |
| `SAFE-02` | **Local runtime:** run all four Core commands and offline doctor after installation with outbound network denied and monitored. Zero network attempts, implicit installs, telemetry, hidden process-state files, or retained logs. Dependencies/assets needed for offline operation must already be inside the distributed installation. |
| `DIST-01` | **Clean distribution:** on every environment declared supported by packaging, install the exact platform artifact into a fresh user directory without a source checkout, dev dependencies, system Node/npm, or a populated package cache; follow the README, execute all four commands, produce the three-file bundle, correct it, and resume a requested Handoff. All pass without maintainer repair. Validate package contents, licenses/notices, version agreement, bundled references/assets, and absence of private material. Exercise explicit setup/doctor/update/uninstall, idempotence, shadowed host registrations, a competing system Node, fresh agent shells, Unicode/space paths, matched updates, handled-failure preservation, abrupt-interruption recovery, and preservation of modified/unowned files and user outputs. Bind observations to bootstrap, platform payload, private runtime, CLI, skill, and inventory hashes. |

Code-coverage percentages do not substitute for the contract matrix. Run deterministic schema, semantic, CLI, and safety tests on every change. Run the complete visual, clean-install, and performance checks on the release candidate and when their dependencies change. Store machine logs as CI/release artifacts, keeping only compact expectations and the evidence index in Git.

## Readability, fidelity, and agent acceptance

Automated geometry gates apply at the default layout scale: zero unintended shape overlap; zero cropped/missing labels; zero labels intersecting unrelated shapes or connectors; zero connectors traversing unrelated activity interiors; correct lane/pool containment. Exclude intentional container nesting, boundary attachment, and endpoints. Each fixture records any unavoidable edge crossings; crossings must remain visually distinguishable, must not obscure labels, and must not increase without review. Do not shrink text below 12 SVG user units to meet a size limit. Larger processes can require panning and zooming; fitting an entire large process into one page is not an acceptance requirement.

For each composition fixture and final discovery result, a reviewer walks the ordinary path and at least two relevant alternate/exception paths where present. Score each dimension from 0 (wrong/unusable), 1 (major repair), 2 (material correction), 3 (usable as generated with cosmetic preferences only), to 4 (clear and complete against the supplied case):

| Dimension | Reviewer checks |
| --- | --- |
| Evidence fidelity | Activities, rules, responsibilities, and outcomes reflect the provided facts or explicit Modeling Decisions. Contradictions and inferences remain distinguished. |
| Process judgment | Scope/perspective and abstraction are coherent; questions concern consequential uncertainty; exceptions and handoffs are represented at the requested detail. |
| Diagram readability | Naming, routing, marker choice, label placement, ownership, and decomposition make the intended scenarios understandable without diagram repair. |
| Practical interaction | A user receives useful artifacts and concise findings, can correct the result naturally, and can export or stop without compulsory questionnaire or status assignment. |

Every dimension must score at least 3; each case's mean must be at least 3.5. Also require zero critical errors: invented consequential process meaning, hidden contradictory evidence, wrong control flow/responsibility, lost correction, missing required artifact, unauthorized replacement, sensitive-content disclosure, unsupported substitution, or false clean/compatibility claim. A high average cannot offset a critical error. Required supplied assertions must have 100% semantic recall; every modeled consequential assertion must have an Evidence Link to source evidence or an explicit Modeling Decision. Advisory cosmetic naming observations remain legal in a Clean Export and are not turned into user approval gates.

Record reviewers and their role honestly. An agent can inspect and pre-score; it must not label that as human validation. Before v0, the maintainer must inspect all eight composition fixtures and the six discovery results, and personally execute one new-user workflow from the distributed artifact using a previously unused synthetic process. The maintainer may be the human reviewer; no external review board is required. Any future usability claim about other users requires actual user evidence.

`HOST-01` runs the real Modeling Skill in the three local CLI surfaces selected by the [release plan](release-plan.md): Codex CLI, Claude Code, and GitHub Copilot CLI. Record host/version, model/version where exposed, OS, discovery mechanism, and CLI/package version. Distribute the six discovery cases two per host. For each host, exercise natural-language creation, local evidence, useful clarification, refinement including rename/add/delete, preview/report presentation, an early Snapshot, Clean Export with advisory findings, and target-specific replacement. One assigned case must contain a meaningful conflict and a later human correction. Validate artifacts with the same automated suite; score the actual interaction above. Zero maintainer repair or hidden generated-input editing. Repeat a failed case after correction; retain the original failure rather than reporting only the successful retry. Desktop, IDE, and cloud surfaces need their own evidence before being advertised.

`HOST-02` requires three real transfers: Codex → Claude Code, Claude Code → Copilot, and Copilot → Codex. Explicitly request a Handoff, open it in a fresh destination session, make one correction, and generate the result. Preserve 100% of unchanged identities, evidence/decision/conflict content promised by the Handoff schema, and intended semantics. No original chat history or source-document access is required. Include the local-evidence and Handoff entry paths on every host, and test untrusted source instructions on every host. A host that cannot complete its declared entry points leaves that advertised surface unqualified and the agreed three-host v0 acceptance incomplete.

Host/model language need not match verbatim. Tool input schemas, artifact correctness, authority boundaries, and scored modeling outcomes must meet the same contract. These bounded runs are release acceptance evidence, not a statistical accuracy benchmark. Ordinary contributor CI does not spend model tokens or require paid host accounts.

## Performance and installation budgets

These targets define “lightweight” as observable behavior. Measure process start through final artifact commit, including validator and renderer startup, excluding model inference, package download, and a tenant operation. On a recorded reference machine with at least two CPU cores and 8 GiB RAM, collect 20 separate CLI runs per scale fixture with one unmeasured preparatory run; use the nearest-rank p95 and report all samples.

| Check | Required budget |
| --- | --- |
| `PERF-01` | `capabilities` and `--help` p95 ≤ 1 second; `validate` on 100 nodes p95 ≤ 2 seconds. |
| `PERF-02` | Complete `generate` p95 ≤ 5 seconds at 25 nodes, ≤ 10 seconds at 100 nodes, and ≤ 30 seconds at 250 nodes. Rendering-only p95 ≤ 5 seconds at 100 nodes. |
| `PERF-03` | Peak aggregate resident memory of CLI and child processes ≤ 512 MiB at 100 nodes and ≤ 1 GiB at 250 nodes. No timeout, crash, omission, or relaxed geometry gate on scale cases. |
| `DIST-02` | Publish measured compressed package size, package-plus-resolved-dependencies size, and clean-install timings. Compressed application payload including bundled production dependencies ≤ 20 MiB; installed application and runtime dependencies/assets ≤ 150 MiB. Measure the private Node runtime separately and publish total platform download/installed sizes including it. If one archive contains both, identify the contributions explicitly. Report the separately installed browser's footprint; never advertise application-only size as complete installation size. No automatic browser download, native compiler requirement, separate database, or additional service. Packaging must satisfy these budgets with the required SVG feature intact. |

Measure Linux and macOS reference results for the release; functional clean-install checks cover Node 24.x on macOS 14+ arm64, Ubuntu 24.04 x64, and Windows 11 x64 under the exact browser prerequisites in the release plan. Record browser and Node patch versions. Windows Server CI is not Windows 11 evidence. A missed budget is an implementation issue to resolve, not evidence that an unmeasured claim is close enough. If the chosen dependencies cannot meet it, replace or reduce them within the agreed functionality; do not make mandatory previews optional.

## Compatibility profiles

Compatibility checks examine the requested model without silently changing it. A model's Consulting Core validity and its target-profile fit are separate facts. Choosing a target must not strip lanes, messages, conditions, events, or documentation automatically; any proposed semantic reduction requires a human Modeling Decision and generates a separately reviewed model.

| Profile identifier | Intended operation and local fit rule | What a verified claim needs |
| --- | --- | --- |
| `bpmn-2.0.2` | Vendor-neutral, self-contained design-time Process/Collaboration with complete DI and no vendor extensions. Entire Consulting Core matrix is required. | `CORE-01`–`CORE-07`; an honest account of same-stack Viewer checks and independent XSD validation. No official OMG conformance certification claim. |
| `sap-signavio-process-manager` | Standard BPMN XML import into Process Manager. Check generic validity, DI completeness, same-file references, and absence of required vendor metadata. No product-specific acceptance can be inferred from passing those checks. | Actual tenant import, visual inspection, and re-export/semantic comparison of the eight composition cases. Process Governance/execution import is a different, excluded claim. |
| `celonis-analysis-conformance` | Conservatively qualify one process using generic activities, Sequence Flows, exclusive/parallel gateways, and none start/end events. Labels must align with an independently supplied activity dictionary if conformance execution is requested. Flag all other constructs as outside this qualification envelope; never imply their semantics survive analysis. | Actual named Analysis/Conformance surface import and control-flow/name comparison of dedicated straight-through, XOR, AND, and rework fixtures. Real conformance execution against event data is separate from import qualification. |
| `celonis-process-management` | Standard BPMN XML import/export into the named Process Management surface. Use the rich composition pack and report tenant/configuration-specific observations. No eBPMN extensions or vendor governance content is generated. | Actual tenant import, inspection, and export comparison of all eight composition cases; record supported losses explicitly. Analysis Conformance results do not qualify this profile. |

The narrow Celonis Analysis envelope is a **consumer test profile**, not a reduction of Consulting Core or a promise that every task subtype/advanced event has identical analysis semantics. An OpenBPMN Clean Export can have target-specific compatibility limitations without becoming invalid BPMN. A user may still export it with those limitations accurately reported.

Official documentation checked on 2026-09-08 establishes import routes, not lossless compatibility. SAP documents BPMN XML import and `bpmn2_0_xml` export through Process Manager's [Import/Export API reference](https://help.sap.com/docs/signavio-process-manager/sap-signavio-process-manager-api/import-export-api-reference). Its published [Process Manager user guide](https://help.sap.com/doc/10ae12665b494798a8a332bcc195689d/SHIP/en-US/sap-signavio-process-manager-user-guide-en.pdf) separately includes BPMN XML import and export. Neither reference is a complete element/DI preservation matrix.

The accessible [Celonis 4.7 Conformance Checker documentation](https://help.celonis.com/cpm47/en/conformance-checker) explicitly identifies activities, connections, exclusive/parallel gateways, and start/end nodes as analysis-relevant and says other components such as annotations are ignored. This is versioned legacy product documentation, not verification of every current cloud surface. The previously researched [Analysis Conformance Checker page](https://docs.celonis.com/en/analysis---conformance-checker.html) redirected to authentication on this check; its current details were not reverified. The conservative profile above avoids treating richer notation as analysis-preserved.

Celonis' first-party [BPMN API page](https://developer.celonis.com/cpm/developer/rest-api/overview/bpmn-api) describes Process Management import/export but now labels that API legacy and recommends the Business Manager APIs for new integrations. This project ships no API integration. Its [configuration documentation](https://developer.celonis.com/cpm/admin/administration/storage-configuration/storage-configuration/) describes configurable BPMN validation and tenant features, reinforcing the need to record the tested configuration. Previously researched [role/eBPMN documentation](https://docs.celonis.com/en/user-roles-by-feature.html) also redirected to authentication during this check. eBPMN stays outside the already approved vendor-neutral profile; no assumed extension compatibility is introduced.

## Tenant qualification procedure

`COMPAT-01` runs every profile's local fit fixtures and checks that `capabilities`, Quality Reports, and documentation distinguish rule-set availability from tenant verification. Every unsupported target concept and unavailable observation must be visible. No generic “SAP/Celonis compatible” badge may stand in for product-, version-, and operation-specific evidence.

`COMPAT-02`, when an authorized tenant is available, uses only the synthetic qualification pack. Import each fixture as a new model into an agreed disposable location; never overwrite a user's model. Record product/surface, exposed version or cloud build/date, relevant settings, operator role, importer options, and artifact hash. Inspect the happy and alternative paths, types/markers, labels, participant/lane ownership, nesting, data, documentation, and all visible DI. Re-export without manual repair when that operation is offered. Record created model identifiers privately and follow the owner's cleanup instruction; the test does not authorize tenant access, account creation, purchases, or an external upload by itself.

Compare re-exported semantic projections, allowing only namespace prefixes, XML ordering, documented default-value expansion, and consistent ID renaming. Build an explicit element correspondence if IDs change; names alone are insufficient where duplicates exist. Required meaning has zero lost or changed elements, relationships, conditions, interruption modes, references, or intentional documentation. Geometry may change if every required element remains visible and the same readability gates pass. Log vendor-added metadata as consumer output; it does not become an OpenBPMN export feature.

Record results separately for import, visual fidelity, semantic preservation, and round trip. A successful HTTP/UI import with missing elements fails preservation. An unavailable export operation remains `not_run` for round trip even if import/visual inspection pass. For the Celonis Analysis profile, compare only its explicitly declared control-flow envelope; no rich-diagram fidelity claim follows from that result. Do not invoke mining/conformance calculations unless separately in scope with suitable synthetic event data.

Publish a compact matrix with fixture IDs and `verified`, `verified_with_limitations`, `failed`, or `unverified` for each tested operation. Attach enough anonymized evidence to reproduce the judgment; link product limitations to the affected concepts. Re-run affected cases when semantics, serialization, layout, target-fit rules, or the consumer version changes. Older tenant observations retain their tested version/date and are never silently relabelled as current.

## Build handoff

Implement the fixture manifest and expected semantic projections before filling out compiler features. Add the positive and negative cases with each semantic family, then complete composition/visual regression, CLI/safety boundaries, installed-package tests, and the six host scenarios. This replaces throwaway prototypes with acceptance work against the real product. Build tickets may close as their checks pass; v0 release closes only when the complete required evidence index passes. Tenant observations can be added as access becomes available without inventing results or postponing the local build.

## Installation checkpoint and release qualification

The installation refinement in issue #41 implements the primary setup path within #32; it does not reduce the full release contract. Reproducible automated lifecycle checks run on available required runners. Actual Codex CLI, Claude Code, Copilot CLI, native Windows 11, and human first-use observations remain separately recorded under #33 when unavailable to ordinary CI. A mocked discovery directory is placement evidence only. Missing licensing, host, native-platform, readability, performance, or compatibility evidence remains unrun/blocked in its existing gate, and no unverified support claim is permitted. Closing an implementation checkpoint never makes these required release gates pass.
