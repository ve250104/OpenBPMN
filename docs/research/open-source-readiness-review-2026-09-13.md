### P2 — Provide a working private vulnerability-reporting route

Verified configuration gap: `GET /repos/ve250104/OpenBPMN/private-vulnerability-reporting` returned `{"enabled":false}`. [`SECURITY.md`, line 5](https://github.com/ve250104/OpenBPMN/blob/22047beb55677145553349d494ade0a5d44cfedc/SECURITY.md#L5) truthfully asks researchers to open a content-free public request because there is no verified private route. Owner action: enable GitHub private vulnerability reporting, verify the form, then replace the fallback with the actual private-report link and ensure the maintainer receives security notifications. [Official reporting configuration](https://docs.github.com/en/code-security/how-tos/report-and-fix-vulnerabilities/configure-vulnerability-reporting/configure-for-a-repository).

### P2 — Add ongoing dependency-advisory monitoring and reviewed updates

Verified configuration gap: the vulnerability-alert endpoint returned HTTP 404 with the explicit message `Vulnerability alerts are disabled.` Repository metadata also reported `dependabot_security_updates.status=disabled`. Only one workflow is tracked; there is no Dependabot/Renovate configuration or separate advisory-scanning job. The current install explicitly uses `--no-audit` ([workflow line 19](https://github.com/ve250104/OpenBPMN/blob/22047beb55677145553349d494ade0a5d44cfedc/.github/workflows/check.yml#L19)). Exact pins and a lockfile support repeatable development but do not notify the maintainer about newly disclosed vulnerabilities.

Recommendation: enable alerts and reviewed security-update PRs; add a low-noise update schedule for npm and GitHub Actions. Preserve exact dependency and full-SHA action pins, and requalify changes—especially the alpha layout dependency—through the existing behavior tests. No automatic merging is needed. GitHub alerts check the default branch as dependencies/advisories change, but do not cover every vulnerability; this observation alone does not establish that a dependency is vulnerable. [Dependabot alerts](https://docs.github.com/en/code-security/concepts/supply-chain-security/dependabot-alerts), [updating Actions with Dependabot](https://docs.github.com/en/code-security/how-tos/secure-your-supply-chain/secure-your-dependencies/auto-update-actions).

Concrete audit result: the accompanying review ran `npm audit --omit=dev --json` and reported one moderate advisory against the direct Ajv `8.17.1` pin ([`package.json`, line 42](https://github.com/ve250104/OpenBPMN/blob/22047beb55677145553349d494ade0a5d44cfedc/package.json#L42)), with no high or critical advisories in that production-dependency audit. GHSA-2g4f-4pwh-qvx6 concerns regular-expression denial of service with `$data` enabled; Ajv's maintainer release confirms the fix in `8.18.0`. This is a known affected package version, not a demonstrated exploitable OpenBPMN path. [`src/input.ts`, line 18](https://github.com/ve250104/OpenBPMN/blob/22047beb55677145553349d494ade0a5d44cfedc/src/input.ts#L18) does not enable `$data`, and a source/script search found no use of it. Schedule a reviewed update to a patched version with the lockfile, notices, and regression checks kept consistent. The audit is a point-in-time advisory check, not proof of absence of other vulnerabilities. [Maintainer's v8.18.0 release](https://github.com/ajv-validator/ajv/releases/tag/v8.18.0), [advisory and affected-version range](https://github.com/advisories/GHSA-2g4f-4pwh-qvx6).

### P2 — Make default-branch checks enforceable

Verified configuration gap: `GET /branches/main/protection` returned `Branch not protected`; repository rulesets returned `[]`. CI currently reports after a push but cannot prevent an unchecked/default-branch update. The two failed runs make this an observed process risk, not a hypothetical requirement for a large team.

Owner decision: after restoring CI, require its unique status check on `main`, block branch deletion/force pushes, and explicitly choose whether administrators are covered. A PR-first workflow is useful, but requiring an independent approval when there is only one maintainer would create a needless deadlock. GitHub supports required checks and protected public branches without a paid plan; administrator bypass behavior needs deliberate configuration. [Protected-branch behavior](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches). These settings cannot be fixed merely by editing the existing workflow.

## Already sound, or optional rather than defects

- All three workflow actions are pinned to full commit SHAs; the workflow grants only `contents: read`. The API also reports read-only default workflow permissions and prohibits Actions from approving PR reviews. These follow GitHub's immutable-action and least-privilege guidance. Keep them when updating action versions. Repository-wide SHA enforcement is currently off; enforcing it is optional extra protection, not evidence that the existing workflow is unpinned. [GitHub secure-use reference](https://docs.github.com/en/actions/reference/security/secure-use).
- Secret scanning and secret-scanning push protection are enabled. Non-provider patterns and validity checks are disabled; those observations are not proof that secrets exist, nor a claim that every secret format is covered. No sensitive alert contents or credentials were retrieved.
- CodeQL default setup reports `not-configured`, and no advanced scanning workflow is tracked. A small JavaScript/TypeScript and Actions scan is a reasonable additional recommendation for the XML/browser/file boundary, but it is not a substitute for the existing adversarial tests or a mandatory badge. GitHub documents Actions scanning as a way to detect vulnerable workflow patterns. [GitHub workflow scanning guidance](https://docs.github.com/en/actions/reference/security/secure-use#using-code-scanning-to-secure-workflows).
- README, MIT license, focused contribution guide, security policy, changelog, synthetic examples, support limitations, and an explicit package allowlist exist. [`CONTRIBUTING.md`, lines 15–29](https://github.com/ve250104/OpenBPMN/blob/22047beb55677145553349d494ade0a5d44cfedc/CONTRIBUTING.md#L15) sets useful behavioral-test, provenance, private-data, and respect expectations. Missing issue/PR templates, a separate Code of Conduct, or CODEOWNERS are not correctness defects. A short bug template asking for versions, a minimal synthetic reproduction, and no private content would be useful when accepting outside reports; no governance bureaucracy is required.
- Low-priority presentation improvement: the repository API reports no About description, homepage, or topics. Add one plain-language description and a few accurate topics so the retained OpenBPMN slug is clearly connected to BPMN Weave. A separate website is unnecessary. No GitHub release exists, and the documentation correctly labels the build unfinished.

## Release-only decisions

For eventual npm publication, prefer trusted publishing with workflow-specific OIDC credentials over a long-lived publishing token. Configure the exact repository/workflow and appropriate owner approval; grant `id-token: write` only to the release job. npm automatically supplies provenance for supported trusted-publishing flows from a public repository to a public package. Preserve the repository's existing exact-tested-archive requirement rather than rebuilding after qualification. These are future release recommendations, not a defect in a development-only repository; npm account ownership and publisher settings were not inspected. [npm trusted publishing](https://docs.npmjs.com/trusted-publishers/), [local release contract](../release-plan.md).

The bundled bpmn-js license has a specific watermark-preservation condition; it is not plain MIT. The exact license is retained at [`assets/runtime/LICENSE.bpmn-js`, lines 13–16](https://github.com/ve250104/OpenBPMN/blob/22047beb55677145553349d494ade0a5d44cfedc/assets/runtime/LICENSE.bpmn-js#L13), and the renderer supplies a linked SVG attribution footer. Preserve the upstream watermark code and inspect its visibility on any future interactive surface; an added footer is not permission to remove the upstream implementation. This bounded check found no new license-text defect. [Exact upstream license](https://raw.githubusercontent.com/bpmn-io/bpmn-js/v18.28.0/LICENSE).

The OMG XSD permission question is an existing release gate, not newly established infringement. OMG still identifies the five bundled schemas as normative machine-readable documents, and its legal page supplies no implied blanket license through website availability. The [existing provenance investigation](distribution-provenance.md) distinguishes verified source bytes from the unresolved interpretation of public redistribution. Resolve that interpretation through suitable review or authorized rights-holder clarification before declaring the distribution gate passed. Do not silently remove validation, substitute a mirror, relicense the files as project MIT, or claim the restriction on copying the PDF conclusively prohibits distributing the separate XSDs. No outreach or legal determination occurred here. [OMG normative documents](https://www.omg.org/spec/BPMN/2.0.2/About-BPMN), [OMG legal notices](https://www.omg.org/legal/), [`THIRD_PARTY_NOTICES.md`, line 14](https://github.com/ve250104/OpenBPMN/blob/22047beb55677145553349d494ade0a5d44cfedc/THIRD_PARTY_NOTICES.md#L14).
